Arquitectura cliente servidor

Los estudiantes abren la aplicación desde sus navegadores. Una única aplicación Node.js con Express entrega los archivos de interfaz y atiende la API. PostgreSQL administrado en Supabase conserva los datos; el servidor se ubica en Render. GitHub Pages entrega únicamente la documentación y los bocetos.

Capas y límites de confianza

CapaDecisión
PresentaciónHTML, CSS y JavaScript sin un framework de componentes obligatorio. Web y API comparten origen.
AplicaciónReglas y permisos centralizados en Express. Sesiones con express-session y connect-pg-simple; contraseñas con Argon2id.
PersistenciaAcceso mediante pg y pool pequeño. Esquema azchat_complete independiente; consultas parametrizadas y TLS con validación de certificado.
Servicios de apoyoProveedor de correo por HTTPS y Web Push invocados desde el servidor. La autorización sigue siendo responsabilidad de AzChat.

Protección del acceso

La cookie contiene un identificador firmado; los datos de sesión están en PostgreSQL. Se regenera al ingresar y usa HttpOnly, SameSite=Lax y Secure en producción. El servidor comprueba el vencimiento absoluto definido en P5 y el origen de las operaciones que modifican datos.

Las credenciales de PostgreSQL, el secreto de sesión y las claves de correo y push pertenecen a configuración privada del servidor. El esquema no debe exponerse a roles públicos de Supabase; RLS complementa la separación. La autorización por estudiante y conversación se aplica en Express. El diseño usa PostgreSQL de Supabase, sin depender de Supabase Auth, Realtime ni un bucket público para archivos.

Recuperación de una cuenta estudiantil

El desafío se vincula al propósito, al navegador y, cuando corresponde, a la cuenta y a su solicitud. Se guarda un HMAC del código, no el código en claro. El servidor bloquea los registros durante la verificación y conserva los intentos incorrectos.

Para un correo no coincidente, el responsable debe contrastar la identidad por un medio conocido antes de decidir. El enlace abre una previsualización y luego exige confirmación. Al completar el restablecimiento se consume la solicitud, se invalidan las demás y se revocan sesiones y suscripciones anteriores.

Alojamiento y operación

El despliegue necesita las dependencias fijadas, el esquema preparado y la configuración privada. El servidor escucha el puerto del entorno y expone /salud, que verifica una consulta simple a la base. Este endpoint comprueba disponibilidad básica, no todas las funciones del chat.

Un alojamiento con suspensión por inactividad puede requerir espera al arrancar. La evaluación debe separar esa espera de la respuesta con servidor activo. Instalar la web añade un acceso en el dispositivo y permite avisos compatibles; el service worker no mantiene una copia del historial ni una cola de envío sin conexión.
